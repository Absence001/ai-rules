# Brief Expander

Превращение расплывчатого запроса в структурированный brief. Источники: Marty Cagan (Four Big Risks), Pavel Samsonov (Three questions).

## Когда использовать

Если запрос расплывчатый (1-3 строки, без нормального ТЗ).

## Принципы

- **Не дополняй запрос сам** — задавай вопросы.
- **Outcome > Output** — переформулируй задачу в **outcome** (что должен сделать пользователь), не в **output** (фича) *(Marty Cagan)*.
- **Alignment > Right** — лучше выровненная команда чем «правильное» решение в споре *(Pavel Samsonov)*.
- Если пользователь отвечает «не знаю» — не выдумывай, помечай как открытый вопрос.

## Порядок

1. Прочитай запрос.
2. Задай 4-6 вопросов одним раундом (приоритет ниже).
3. После ответов — резюме 3-5 пунктов.
4. Если контекст всё ещё слабый — следующий раунд (с уточнениями).
5. Когда достаточно — запиши `artifacts/brief.md` (контракт см. `meta/artifact-contracts.md`).

## Приоритет вопросов

| Приоритет | Тема |
|---|---|
| 1 | **Outcome** — что пользователь должен сделать, какая цель? |
| 2 | Аудитория и контекст использования |
| 3 | Ограничения (технические / временные / организационные) |
| 4 | Бизнес-цели |
| 5 | Fail criteria — что считаем провалом |
| 6 | Метрики успеха |

## Four Big Risks (Marty Cagan) — pre-flight check

Перед стартом проекта **явно** оцени каждый риск:

| Риск | Вопрос | Кто отвечает |
|---|---|---|
| **Value** | Будут ли вообще использовать? | Product / Brand |
| **Usability** | Поймут ли как пользоваться? | Designer |
| **Feasibility** | Можно ли построить за время/бюджет? | Engineer |
| **Business Viability** | Работает ли для legal / finance / sales / marketing? | Stakeholders |

> *«Discovery exists to kill all four before delivery starts»* — Cagan

**Если хоть один риск не закрыт** — идея не готова к разработке. Фиксируй это явно в brief.

## Three Samsonov questions

Перед любым серьёзным решением задай:

1. **Какие у нас assumptions?** (явно перечисли)
2. **Как мы узнаем что мы неправы?** (что должно случиться)
3. **Что мы сделаем, если окажемся неправы?** (план B)

> *«how will we know if we are wrong in our assumptions and what are we going to do about it?»* — Samsonov

Без этих трёх ответов — решение = ставка вслепую.

## JTBD properly

> *«no one wants to use a product»* — Samsonov. Пользователи не хотят использовать продукты. Они хотят достичь цели.

JTBD на правильном уровне:
- ❌ Слишком узкий: «нажать кнопку Submit»
- ✅ Правильный: «закрыть месяц по финансовому отчёту»
- ❌ Слишком широкий: «быть успешным в работе»

**Test:** если JTBD можно решить **без вашего продукта** (бумагой, Excel'ем, конкурентом) — это правильный уровень. Продукт — инструмент, не самоцель.

## Outcome vs Output

| Output (плохо) | Outcome (хорошо) |
|---|---|
| «Сделать onboarding flow» | «Чтобы 80% новых пользователей дошли до first value за <3 минут» |
| «Добавить dashboard» | «Чтобы admin видел статус системы за 1 взгляд» |
| «Редизайн checkout» | «Снизить cart abandonment с 65% до 50%» |

**Правило:** в `artifacts/brief.md` зафиксировать **outcome**, не output.

## Структура `brief.md`

См. `meta/artifact-contracts.md` для детального контракта. Минимум:

- Контекст и outcome
- Целевая аудитория
- JTBD (правильного уровня)
- Бизнес-цели
- **Four Big Risks** оценка
- Three Samsonov questions ответы (или явно «не знаем»)
- Ограничения
- Fail criteria
- Метрики успеха
- Риски / открытые вопросы

## Anti-patterns

| Anti-pattern | Симптом |
|---|---|
| Дополнять запрос своими догадками | Делаем не то |
| Output вместо outcome в brief | Feature factory mode |
| Игнорировать риски Cagan | Высокая вероятность провала на ровном месте |
| Пропустить Three Samsonov | Ставка вслепую |
| «JTBD: нажать кнопку» | Не уровень JTBD |
| Не записать assumptions явно | Позже не сможем проверить |

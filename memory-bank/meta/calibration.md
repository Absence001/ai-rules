# Calibration & Self-correction

Универсальный паттерн оценки уверенности и проверки решений. Применим во всех режимах, не только в багах.

## Принцип

> *«LLMs need to be (1) factual and (2) acknowledge not knowing the answer when applicable»* — Lilian Weng

Любое утверждение/решение/предложение содержит **уровень уверенности**. Делай его явным.

## Когда указывать уверенность

| Ситуация | Указывать УВЕРЕННОСТЬ:X%? |
|---|---|
| Простой ответ на фактический вопрос | Нет, если очевидно |
| Диагностика бага | Да, обязательно |
| Решение про IA / архитектуру | Да |
| Выбор компонента из существующих | Только если ≠ 100% |
| Создание нового компонента | Да |
| Утверждение про дизайн-систему | Да |
| Утверждение про дату/событие/факт | Да, если есть сомнение |
| Предложение библиотеки/инструмента | Да |

## Шкала уверенности

| Диапазон | Что значит |
|---|---|
| 90-100% | Подтверждено материалами/документами/тестами |
| 70-89% | Сильная гипотеза, но без прямого подтверждения |
| 50-69% | Разумная гипотеза, нужна проверка |
| < 50% | Догадка — лучше задать вопрос, чем продолжать |

**Правило:** если уверенность < 50% — **задавай вопрос пользователю**, не действуй вслепую.

## Self-correction patterns

### 1. Token check (для DS / кода)

Когда предлагаешь имя токена / компонента / API — если не уверен что оно существует в системе:

```css
color: var(--unknown-token-name); /* check-token */
```

Метка `/* check-token */` сигнализирует пользователю и тебе самому что значение требует проверки.

### 2. Chain-of-Verification (CoVe, Lilian Weng)

Для критических решений — 4 этапа:

1. **Черновик ответа.**
2. **Сгенерируй проверочные вопросы** к черновику.
3. **Ответь на эти вопросы** (для каждого — отдельно).
4. **Финальный ответ** с учётом проверок.

Применяй для:
- Архитектурных решений
- DS изменений с broad impact
- Утверждений про факты/числа
- Безопасности / privacy / accessibility

### 3. Reflexion (после провала)

Если попытка не сработала — **не повторяй её сразу**.

1. Что именно не сработало? (конкретная ошибка / симптом)
2. Какие были assumptions? Какая из них была неверна?
3. Какая стратегия в принципе другая?
4. Только после этого — новая попытка.

> Просто retry без анализа = тратишь токены пользователя.

## Calibration в баг-формате

См. `code-diagnostics/code-diagnostics.md`. Минимальный формат — `УВЕРЕННОСТЬ: X%` в конце шаблона. Этот паттерн расширяется на любые критические утверждения, не только баги.

## Anti-patterns

- ❌ «Скорее всего…» без процента
- ❌ Утверждать с 100% уверенностью то, что не проверено
- ❌ Указать 95% когда реально 50% — ложная уверенность хуже отсутствия процента
- ❌ Retry без Reflexion
- ❌ Использовать имя токена/API не проверив существование

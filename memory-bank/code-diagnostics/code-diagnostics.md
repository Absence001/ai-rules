# Code Diagnostics

Диагностика и исправление багов. Источники: Lilian Weng (ReAct, Reflexion), общая практика.

## Два режима (важно)

| Режим | Триггеры | Поведение |
|---|---|---|
| **Diagnosis** | «Почему не работает?», «Что не так?», «Найди причину», «Объясни ошибку» | Diagnose → plan → confidence% → **спросить перед fix** |
| **Direct fix** | «Почини», «Исправь», «Fix», «Реализуй» | Read context/logs/config → minimal fix → test → отчёт. **Без дополнительного вопроса**, если fix не затрагивает high-risk actions (см. `AGENTS.md` Stage gates: deps, deletion, scope/architecture, DS change, Figma write) |

Главный принцип для **обоих режимов:** диагностика идёт **до** правки. Direct fix всё равно начинается с понимания root cause, просто не требует дополнительного confirmation step после диагностики.

## Когда использовать

Баги, ошибки, неожиданное поведение, конфиги, логи, зависимости, запуск проекта.

## Главный принцип

**Сначала найди проблему, потом предлагай правки.** Не fix до того как понятна root cause.

## ReAct + Reflexion подход

Используй формальный цикл *(Lilian Weng)*:

```
Thought      → подумать что может быть причиной
Action       → проверить (read code/config/logs)
Observation  → что увидел
→ если не понятно → новый Thought
→ если ясно → формат ответа ниже
```

**Если попытка не сработала** — Reflexion:
1. Что не сработало конкретно?
2. Какая assumption была неверна?
3. Какая стратегия другая?
4. Новая попытка.

Слепой retry = трата токенов.

## Обязательный формат ответа (зависит от режима)

### Diagnosis mode

```markdown
- ПРОБЛЕМА: <конкретная проблема>
- ГДЕ ИМЕННО: <файл:строка / конфиг / лог>
- КАК БУДЕМ РЕШАТЬ (план): <короткие шаги>
- ЧТО ИЗМЕНИТСЯ ПОСЛЕ: <ожидаемое поведение>
- КАК ПРОТЕСТИРОВАТЬ ПОСЛЕ РЕШЕНИЯ: <конкретные действия в боте/UI/тестах>
- УВЕРЕННОСТЬ: X%
- ВОПРОС: Могу ли я начать исправление?
```

**Diagnosis mode:** код не менять до явного «да» от пользователя. Финальный `ВОПРОС` обязательный.

### Direct fix mode

```markdown
- ПРОБЛЕМА: <конкретная проблема>
- ИЗМЕНЁННЫЕ ФАЙЛЫ: <список>
- ЧТО СДЕЛАНО (минимальный fix): <короткое описание>
- КАК ПРОТЕСТИРОВАНО: <фактические команды / шаги выполнены>
- УВЕРЕННОСТЬ: X% (актуально для решений уровня fix)
- ОСТАТОЧНЫЙ РИСК: <что может ещё всплыть / что я не покрыл>
```

**Direct fix mode:** финальный `ВОПРОС` **не нужен** — пользователь явно попросил fix. Но **остановиться и спросить**, если в процессе fix требует high-risk action (deps, deletion, scope/architecture, DS change, Figma write — см. `AGENTS.md` Stage gates).

## Правила

### Diagnosis-first

- **Сначала найти проблему** в коде / конфиге / логах
- До этого **не предлагай правки** даже если очевидно
- **Проверь гипотезу 3 раза:**
  1. В коде (исходник)
  2. В конфиге (env vars, settings)
  3. В логах / симптомах (что реально происходит)

### Calibration (см. `meta/calibration.md`)

УВЕРЕННОСТЬ — обязательная часть формата:

| Диапазон | Что значит | Действие |
|---|---|---|
| 90-100% | Подтверждено в коде/логах | Можно предлагать fix |
| 70-89% | Сильная гипотеза без прямого подтверждения | Указать что ещё проверить |
| 50-69% | Разумная гипотеза | Указать что неопределенно, попросить контекст |
| < 50% | Догадка | **Не предлагать fix**. Задать вопрос |

### Stage gate (зависит от режима)

**Diagnosis mode:**
- ВОПРОС: «Могу ли я начать исправление?» — обязательная финальная строка формата
- Не править код до явного «да» от пользователя

**Direct fix mode:**
- Не задавай confirmation question — пользователь явно попросил fix
- Но **всегда останавливайся**, если fix требует high-risk action (deps install, file deletion, scope change, architecture rework, DS change, Figma write)
- В любом случае: изменения минимальные — не рефактори всё подряд
- После правок: отчёт что/почему/какие файлы/как проверить

## Reflexion в багах

Если первая гипотеза не подтвердилась:

```markdown
- ГИПОТЕЗА 1 НЕ ПОДТВЕРДИЛАСЬ: <что я думал и почему оказалось не так>
- НОВАЯ ГИПОТЕЗА: <другая стратегия диагностики>
- ПЛАН ПРОВЕРКИ: <конкретно что смотрю>
```

Делает thinking process видимым.

## Common bug patterns

| Симптом | Сначала проверь |
|---|---|
| «Не работает» (vague) | Запроси: что именно ожидал? Что увидел? Шаги воспроизведения? |
| TypeError | Типы данных, optional chaining, null/undefined handling |
| 404 / route не найден | Routing config, dynamic params, case sensitivity |
| State не обновляется | useState vs setState, async timing, dependency arrays |
| Layout сломан | CSS specificity, flex/grid parent, media queries |
| Запрос не идёт | Network tab, CORS, credentials, headers |
| Бесконечный loop | useEffect deps, recursion base case |
| Стало медленно после изменения | Bundle size, re-renders, memo'ization |

## Не делать

- ❌ Предлагать fix не найдя problem
- ❌ «Может быть это X» без проверки
- ❌ В diagnosis mode — менять код без подтверждения
- ❌ В direct fix mode — игнорировать high-risk actions и менять архитектуру / удалять файлы / ставить пакеты без вопроса
- ❌ Рефакторить «по пути» (минимум изменений в обоих режимах)
- ❌ Retry без Reflexion
- ❌ УВЕРЕННОСТЬ: 100% если не проверено
- ❌ УВЕРЕННОСТЬ без диапазона (только «уверен» / «не уверен»)

# IA Rules

Информационная архитектура: sitemap, navigation, hierarchy. Источники: Pavel Samsonov, Marty Cagan, общие IA практики.

## Когда использовать

После `artifacts/research.md`, **перед** дизайном экранов и flow.

## Главный принцип

> *«designers ended up visually solving the worst information architecture you have ever seen»* — Samsonov

**Сначала структура, потом визуал.** Полированный визуал не лечит сломанную IA.

## Фиксированный порядок (Samsonov)

```
Sitemap → Wireframe → Screen
```

**Не прыгай в UI до IA.** Любая попытка решить IA-проблему визуальным приёмом — провал.

## Порядок работы

1. Прочитай `brief.md`, `srgid.md`, `research.md`.
2. Выдели **главный JTBD** (см. `discovery/brief-expander.md` про правильный уровень).
3. Определи **главный сценарий** (тот который закрывает максимум JTBD).
4. Определи **главный экран** (где сценарий начинается).
5. Определи **главное действие** пользователя.
6. Построй **sitemap** максимум до 2 уровней.
7. Построй **user flow** для главного сценария.
8. Запиши `artifacts/ia.md`.

## Правила IA

### Структура

- Каждой задаче — **минимально необходимый** набор экранов.
- **Nice-to-have не превращать в экраны.** Если можно — inline, drawer, modal.
- Если сценариев несколько — выбираем тот, который закрывает **максимум** JTBD.
- Sitemap до **2 уровней** — глубже = пользователь теряется.

### Главное действие test

**Test:** если за 3 секунды на главном экране пользователь **не понимает** что делать → IA сломана.

Решение:
- Один primary CTA на экран
- Visible не значит «большой и яркий», значит «понятный из контекста»
- Иерархия через несколько сигналов (см. `craft/craft-core.md`)

### Метки = слова (Samsonov)

> *«labels are words»* — слова важны как код

- Метки на **языке пользователя**, не на жаргоне команды
- Test: если пользователь не из вашей команды НЕ понимает метку → меняй
- Не использовать internal naming (например `crm-pipeline-stage-3` как метка)

## Связи > Элементы

**Главное в IA — не что есть, а как связано.** Перед wireframe ответь:

- Откуда пользователь приходит на этот экран?
- Куда он может пойти отсюда?
- Что приходит/уходит вместе с ним (state, data, context)?

Если связи неясны — sitemap недостаточно проработан.

## Когда экран, когда modal, когда flow

См. `flow-design.md` для decision table.

Краткое правило здесь:
- **Экран** — самостоятельная задача со своим контекстом, можно ссылаться
- **Modal** — узкая подзадача, прерывает текущий flow
- **Drawer** — контекст рядом с основным экраном (фильтры, детали)
- **Inline expand** — дополнительная инфа без потери контекста
- **Wizard** — последовательная задача N шагов где порядок важен

## Что НЕ делать

- **Не добавлять экраны** «потому что красиво» или «может пригодится»
- **Не строить sitemap глубже 2 уровней** — пользователи теряются
- **Не визуально лечить** IA-проблему (Samsonov)
- **Не использовать жаргон** в метках
- **Не делать modal в modal** (sign of broken IA)
- **Не делать wizard когда хватит одного экрана**

## Three Samsonov questions перед IA

Применить из `discovery/brief-expander.md`:

1. Какие assumptions про user behavior мы делаем?
2. Как узнаем что мы неправы (пользователи теряются / не доходят)?
3. Что сделаем если окажемся неправы?

## Структура `ia.md`

См. `meta/artifact-contracts.md`. Минимум:

- Главный сценарий
- Главный экран
- Главное действие
- Sitemap до 2 уровней
- User flow шагами
- Что **исключено** как nice-to-have (явно)
- Open questions / assumptions

## Anti-patterns

| Anti-pattern | Симптом |
|---|---|
| Полированный визуал поверх сломанной IA | Pretty mess (Samsonov) |
| Buried navigation (3+ уровня) | Пользователи теряются (Cagan, usability risk) |
| Метки на жаргоне команды | Confusing |
| Modal в modal | IA broken |
| Wizard когда хватает одного экрана | Overengineering |
| Nice-to-have как полные экраны | Раздувание scope |
| Sitemap без real user flows | Абстракция оторвана от задач |
